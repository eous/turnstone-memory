## ✅ FINAL ARCHITECTURE DECISION (2026-05-31) — ENDPOINT-ONLY (supersedes the in-process plan below)
User decided: **NO in-process inference in Turnstone** — it has always been orchestration-only, and bundling onnxruntime/vendored weights would break that invariant. Reranking is supported **ONLY via an endpoint backend**, like every other model in Turnstone: a `reranker` model role → a **Cohere/Jina-compatible rerank endpoint** (self-hosted vLLM/TEI/llama.cpp, or hosted Cohere/Jina/Voyage), base_url+model+write-only key, in the admin Models sub-tab. **Disabled by default** (no endpoint → reranking off, gated like web_search-without-SearXNG).
- **DROPPED as moot:** vendored int8 weights, Git LFS, the weight-redistribution/MS-MARCO licensing analysis, onnxruntime/tokenizers/fastembed deps + `turnstone[rerank]` extra, model download/cache/offline mgmt + fetch-via-admin/BYO-disk paths, the int8/fp16/fp32 tier model, in-process CPU-latency concerns. (onnxruntime-gpu already rejected.)
- **STILL VALID BELOW AS REFERENCE (not the chosen path):** the spike's latency/size/quality numbers; the OSS-reranker landscape; and esp. the **Cohere/Jina wire-format facts — now THE core**, since one Cohere/Jina HTTP client covers vLLM/TEI/llama.cpp/Cohere/Jina/Voyage.
- **STILL IN PLAN (unchanged):** both consumers (web_search snippets = ship first/simpler; web_fetch chunk-selection — **chunking stays in Turnstone**, only *scoring* is remote: chunk→send (query,chunks)→scores→top-k); the source-agnostic `rank(query,candidates)->scores` client interface (now a thin HTTP client); size-gate for web_fetch; rerank only SearXNG `data["results"]` (leave answers/infoboxes); **MEASURE web_search lift** (now costs a network hop → must earn it); admin sub-tab under Models (pure endpoint/role config).
- **Airgap:** not lost — run a reranker on the local vLLM/TEI, same as airgapped installs already run their chat LLM. **Tradeoff (accepted):** reranking needs infra → off for casual installs; near-zero friction if already running vLLM; hosted Cohere/Jina sends data off-box (local-first users point at own vLLM/TEI).
- **Transport caveat retained:** config/role shape mirrors other models, but rerank is NOT OpenAI-spec — needs its own Cohere/Jina HTTP client, not `client.embeddings.create()`/the chat path.
- **Build shrinks to:** `RerankClient` (Cohere/Jina HTTP) + `reranker` model role + 2 call-sites (web_search, web_fetch) + admin sub-tab. No weights, no inference deps, no distribution problem.

2026-05-31 scoping for the reranker. Researched the 2026 rerank API + model landscape against primary sources.

**THE load-bearing correction — reranker ≠ "just another model role like embedding":**
- **Embeddings ARE in the OpenAI spec** (`client.embeddings.create()`), so the planned embedding role rides the existing OpenAI/provider SDK lane.
- **Reranking is NOT in the OpenAI spec** — there is no `client.rerank()` and no OpenAI rerank endpoint. OpenAI's own guidance is "build it yourself with a cross-encoder" (their cookbook does it over chat). So a reranker-role-pointed-at-a-provider is a **brand-new client lane**, not a reuse of embedding plumbing.
- The de-facto rerank wire standard is **Cohere's `/v2/rerank`** (`{model, query, documents, top_n}` → `results[].relevance_score`); **Jina and Voyage mirror it**. There is no "OpenAI-compatible rerank" — when vLLM/TEI/llama.cpp advertise an OpenAI-compatible server, their rerank route is a **separate Cohere/Jina-shaped `/rerank`** bolted alongside the OpenAI routes.

**Commercial rerankers (verified 2026):** OpenAI **no**, Anthropic **no**, xAI **no**. **Google = yes but Vertex AI Ranking API / Discovery Engine ONLY (`semantic-ranker-default/-fast-004`), NOT the Gemini API** — separate GCP service + ADC/service-account auth, won't fall out of the Gemini provider for free; least relevant to a local box. The real rerank-API market is **Cohere** (Rerank 4 `rerank-v4.0-pro/-fast` + `rerank-v3.5`), **Jina** (`jina-reranker-v2`/`m0`), **Voyage** (`rerank-2.5`/`-lite`), **Mixedbread** (`mxbai-rerank-base/large-v2`, also open-weight Apache-2.0).

**vLLM = yes, cleanly:** `/rerank`,`/v1/rerank`,`/v2/rerank` (Cohere+Jina compatible) + `/score`; serves both seq-cls cross-encoders (bge-reranker) and LLM-style (Qwen3-Reranker, mxbai, Nemotron). TEI and llama.cpp (`--reranking`→`/v1/rerank`) also serve rerank; **Ollama does NOT in stable yet** (PR open — don't assume). **One Cohere/Jina HTTP client covers vLLM+TEI+llama.cpp+Cohere+Jina+Voyage** (same shape).

**Model sizes — small enough for in-process:** `ms-marco-MiniLM-L-6-v2` 22M (**23 MB int8 ONNX**, Apache, English, the featherweight default); `bge-reranker-v2-m3` 568M (~0.5 GB int8, **Apache, multilingual**, the strong tier — note fp32 safetensors is 2.27 GB, ship the int8/ONNX build); `Qwen3-Reranker-0.6B` / `mxbai-rerank-base-v2` 0.5–0.6B (Apache). **License trap: `jina-reranker-v2` is CC-BY-NC-4.0 (non-commercial) — avoid for OSS.** Rerank a top-k candidate set (20–50), not hundreds, to stay sub-second on CPU.

**DECISION (fits local-first/no-telemetry/CPU/minimal-scope):**
- **Default backend = in-process via FastEmbed** (onnxruntime, **NO torch**) + an **Apache-2.0** model (MiniLM-L6 English / bge-reranker-v2-m3 multilingual). NOT sentence-transformers `CrossEncoder` as default (drags in torch ~GBs). Likely gate behind an extra `turnstone[rerank]` (mirror `turnstone[anthropic]`).
- **Distribution: lazy-download-from-HF-and-cache, pinned by commit hash, NOT Git LFS** (LFS taxes every clone/CI + burns GitHub's ~1 GB quota). Support `HF_HUB_OFFLINE`/`TRANSFORMERS_OFFLINE` + a local-path override for air-gap. Inference makes zero network calls; only first-run download touches HF (pre-seedable).
- **Wiring is NOT a clone of the embedding role:** a `search.reranker_backend` selector = **`in_process` (default) | `endpoint` (Cohere/Jina HTTP lane → vLLM/TEI/Cohere/…) | `none`**. Models→Roles entry is a *backend + model* picker, not a provider-alias dropdown; the alias/provider UX only matters when backend=`endpoint`.
- **Build order (minimal-scope-first):** ship the **in-process default first** (a `rerank(query, passages)->scores` fn + the size-gated call-site in `_exec_web_fetch` `session.py:12415`); DEFER the endpoint client lane + full provider UX until someone needs to serve a bigger reranker. Prove the reranker in-process before any fusion/serving infrastructure.

**SPIKE RESULTS (VERIFIED 2026-05-31 — FastEmbed 0.8.0 / onnxruntime 1.26 / py3.12; real 177 KB WW2 wiki page → 233 chunks; throwaway venv in /tmp, NOT committed):**
- **Works + int8 preserves quality:** cross-encoder ranked an injected needle #1/41 with huge margin — MiniLM fp32 9.30, **int8 9.34** (identical), bge-base 2.66 — all vs strongly-negative distractors. Quantization did NOT degrade ranking.
- **Sizes — FastEmbed downloads fp32 BY DEFAULT, not int8:** MiniLM-L-6-v2 = **86.8 MB fp32 / 22.1 MB int8**; bge-reranker-base = **1.06 GB fp32** (~0.27 GB int8 est.); bge-reranker-v2-m3 ≈ 2.3 GB fp32 / ~0.5–0.6 GB int8 est. To ship int8 you feed FastEmbed the quantized ONNX (`Xenova/…/onnx/model_quantized.onnx`) OR use **raw onnxruntime + `tokenizers` (~30 lines)** — the latter also escapes FastEmbed's curated list, letting you load `onnx-community/bge-reranker-v2-m3-ONNX` directly. Deps total 217 MB, **no torch** (confirmed).
- **Latency** (shared/contended 192-core host → RATIOS trustworthy, ABSOLUTES pessimistic ~6–10× a normal core; benchmark on target HW): MiniLM per-pair fp32 ~58 ms(1t)/~23 ms(4t), **int8 ~28 ms(1t)/~16 ms(4t)** → int8 ~4× smaller + ~1.5–2× faster, same quality. Cost **linear in N**. bge-base 4–16× slower (~250 ms/pair @1t). int8@4t practical: top-20≈310 ms, top-50≈780 ms, top-100≈1.6 s, top-200≈3.2 s.
- **CONFIRMED build decisions:** commit to in-process; **default to int8 ~22 MB** (supply quantized model, don't rely on FastEmbed's fp32 default → nudges toward raw onnxruntime+tokenizers); **rerank bounded top-k 20–50 gated on page size, 2–4 threads**, NEVER synchronously rerank a full page (200 chunks = 3–9 s); MiniLM-L6 = featherweight English default, bge-reranker-v2-m3 int8 = opt-in multilingual tier (~25× the download, opt-in not default).
- **Big-lab OSS reranker landscape (VERIFIED 2026-05-31):** among big general-purpose labs only **Qwen/Alibaba** ships first-party open reranker weights (Qwen3-Reranker 0.6/4/8B Apache + gte-multilingual-reranker Apache); **BAAI** bge-reranker is the institutional open standard (base/large MIT, v2-m3/v2-gemma/v2-minicpm Apache); OpenAI/Google/Meta/Anthropic/Mistral/DeepSeek ship NONE (Google's is the proprietary Vertex Ranking API). BUT Qwen3-Reranker is **LLM-style → needs torch/vLLM** (community ONNX/GGUF have correctness pitfalls), so it's the wrong runtime for the lean no-torch default; the clean ONNX-no-torch path is the classic cross-encoders (MiniLM, bge-reranker base/large/v2-m3, jina-v1). NVIDIA partial (llama-nemotron-rerank-1b open under NVIDIA Open Model License; NV-RerankQA NIM-gated). Cohere closed/API-only.
- **Licensing scope of the spike:** model-card license metadata was recorded, but the spike did
  not establish redistribution rights for converted weights or resolve training-data terms.
  The endpoint-only architecture selected later does not vendor weights. Any future bundling
  proposal needs its own documented source licenses, conversion provenance, and licensing decision.
- **Size/mechanism:** int8 MiniLM = **23 MB → vendorable** (the earlier no-Git-LFS caution was about 300–600 MB models). Ship via a **separate optional weights package pulled by `turnstone[rerank]`** (extras gate deps → only opt-in users get it), or Git LFS. **Do NOT vendor `bge-reranker-v2-m3` int8 = 571 MB** → keep it download/BYO + local-path override for airgap.
- **SECOND CONSUMER — web_search result reranking (verified against code 2026-05-31):** the reranker also fits the SearXNG `web_search` tool, *more cleanly* than web_fetch. `turnstone/core/web_search.py` `_format_searxng` pulls `data["results"]` (SearXNG's merged list across ~200 engines, typically tens of hits) then keeps only `results[:max_results]` (default 5) by SearXNG's own cross-engine position aggregation. → **Rerank the already-returned pool and pick top-k = near-zero-cost lift** (no extra search call); insertion point is that one `[:max_results]` slice (~`web_search.py:123`). No chunking, no size-gate (results are pre-discretized title+≤500-char content); latency hidden behind the SearXNG HTTP round-trip. Caveats: (1) reranking SNIPPETS not page content → bounded lift, MEASURE before default-on (SearXNG ranking isn't bad); (2) it's RERANK not RRF (one already-engine-fused list); (3) `WebSearchClient.search()` returns formatted markdown not structured hits → minimal insertion is inside `_format_searxng` (SearXNG-only; MCP backend returns opaque text), backend-agnostic version needs the client to return structured results. **Strategic:** two consumers (web_fetch chunks + web_search snippets), both query-time/ephemeral/no-storage/same core → strongest argument to build a source-agnostic `rank(query, candidates)->scores` primitive. **web_search is the better FIRST consumer** (simpler, proves the core); build order = reranker primitive → web_search → web_fetch chunk selection.
- **PRODUCTIZATION (proposal review 2026-05-31):** user proposed vendoring int8 + optional rerank for web_fetch & web_search, admin sub-tab under Models, default-on, plus a "500MB fp32 model for GPU installs" and maybe onnxruntime-gpu for int8. Corrections/decisions:
  - **Don't conflate 3 orthogonal axes:** model (MiniLM↔bge-v2-m3 quality) / precision (int8↔fp16↔fp32) / device (CPU↔GPU). The "500MB" was bge-v2-m3 **int8**, NOT fp32 (its fp32 ≈ 2.3GB). **REJECT fp32 as a deployment artifact** — for inference int8 wins on CPU (faster+4×smaller+no quality loss, measured) and fp16 wins on GPU (½ size, same accuracy). Quality tier = bigger MODEL in fp16/int8, never fp32.
  - **onnxruntime-gpu for int8 = category mismatch, REJECT:** onnxruntime CUDA EP targets fp16/fp32; CPU-quantized int8 ONNX falls back to CPU / runs unaccelerated (real GPU int8 = TensorRT EP + calibration). And MiniLM (22M) is too small to beat GPU launch/transfer overhead. **GPU tier = the ENDPOINT backend (vLLM/TEI), not bundled onnxruntime-gpu** — GPU-rich installs already run vLLM; endpoint reuses it + unlocks LLM-style models that don't fit in-process ONNX (Qwen3-Reranker). onnxruntime-gpu+fp16-bge is a technically-possible 4th option but duplicates vLLM and drags CUDA into the install — skip unless someone wants in-process GPU w/o a serving stack, and only as a separate install path, never the default wheel.
  - **TIER MODEL:** (1) Default = MiniLM-L6 int8/CPU in-process, **vendored 22MB**, everyone; (2) Quality-CPU = bge-reranker-v2-m3 int8/CPU in-process, fetch-via-admin or BYO-disk 571MB, multilingual/no-GPU; (3) Quality+speed-GPU = bge-v2-m3 or Qwen3-Reranker fp16, **endpoint (vLLM/TEI)**, GPUs-to-burn.
  - **Default-on cost:** moves deps (onnxruntime-CPU + tokenizers + 22MB weights) from optional `turnstone[rerank]` extra into BASE install (~+80MB) — conscious trade vs lean-install value; **lazy-load the model** (first rerank, not startup) so idle installs pay nothing at runtime. web_fetch default-on clearly good (gated by size, replaces truncation); **web_search default-on but MEASURE the snippet-rerank lift** vs SearXNG native (may not beat it → just latency); per-tool off switch; rerank only `data["results"]`, leave `answers`/`infoboxes` untouched.
  - **Admin sub-tab under Models** = right home: per-tool on/off, tier/model select, backend (in-process↔endpoint), weights mgmt (fetch big model w/ progress job, or disk-path for airgap).
