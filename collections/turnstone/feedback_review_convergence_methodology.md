Three lessons from the #817 background-shells review marathon (6 workflow rounds + 1 unprimed single agent, ~50 confirmed findings), the methodology one straight from the maintainer.

**1. Delta-steered ≠ convergence (the maintainer, 2026-07-10).** From round 3 on, my review prompts targeted "the previous round's fixes" and DESCRIBED my fixes in my own framing. Declining severity under that regime measures attention allocation, not code quality — finders pointed at smaller, newer code find smaller findings, and priming them with my fix narrative biases verify-my-story over discovery. Proof: an unprimed round found a showstopper (unregistered `_source` → every notice delivery raised ValueError) that FIVE delta-steered rounds missed, plus a pre-existing CLI leak outside the diff. **How to apply:** steered rounds are for verifying fixes; the SHIP GATE is a full-surface review with a minimal target ("review this diff"), no fix ledger, no round history, no "N defects already found."

**2. Temporal features get an event-model design pass first.** A feature that adds a time axis (background anything: events land while nothing is running) will stress every rail it rides. The NudgeQueue needed quiet-channel/seq/requeue semantics that were evolved across three review rounds instead of designed once — each fix moved an invariant somewhere else (notice preservation broke cancel quiescence broke the watch cap broke chronology). Before coding: enumerate the delivery rails and design their full event model (seam eligibility, wake eligibility, cancel scoping, ordering, failure recovery) up front. Corollary: rails with a single producer have implicit contracts; the second producer is a fuzzer.

**3. Queue assertions don't test delivery.** The #817 notices were undeliverable end-to-end (ValueError at every seam) while ~120 tests passed, because they asserted `pending()`/`drain()` state and never drove real emission (`make_system_turn` validates `_source` only at the emission layer). Any artifact that transits a queue/registry needs at least one test exercising the FULL consumer path to the terminal side effect.

**4. Even UNPRIMED, one clean round ≠ convergence (obo #830 loop, 2026-07-12, 12 rounds).** Every round used a minimal unprimed target ("diff between main...branch") — yet the confirmed-correctness count was NON-monotonic: 15,10,1,**0**,3,0,5,2,4,1,0. Round 4 hit 0 and was NOT converged — round 5 found a SECURITY bug (a same-type static edit could inject an `authorization_server_url` that survived a flip to oauth_user → attacker-AS redirect) and round 7 found a DEAD FEATURE. Different finder angles surface different bugs each pass; a serious defect stays invisible until a finder probes its exact angle. **How to apply:** declare convergence only after **2+ consecutive** rounds with zero confirmed correctness, and expect the count to bounce (a big security-sensitive diff yields a few new edge cases per round with generally decreasing severity — that IS the healthy tail, not a failure). Many findings are follow-ons from your OWN prior fixes (fix→new-edge chains), especially in complex sub-features. Fix the clearly-beneficial cleanups, DOCUMENT the trade-off ones as accepted (don't thrash), and stop on the correctness signal — not on a mythical zero-findings round.

**4b. The precise stopping rule (the maintainer, 2026-07-13, #827 branch).** The 2-consecutive-clean criterion is on the CORRECTNESS axis only: two consecutive rounds with **0 confirmed correctness findings** converge, even if those rounds still surface cleanup/performance items (fix or document those; they don't reset the counter). ONE exception ends it early: a **truly empty report** — zero findings in every category — is terminal on its own (a flawless run), no confirming round needed. A cleanup-only round is NOT that; it still needs the second correctness-clean round.

**Why:** correctness is the primary goal, and everything else is polish that happens only after everything is correct (the maintainer). The rule *guarantees* every push ends with two polish-only rounds: any correctness find restarts the clock, so the final two rounds are by construction spent fixing/dispositioning non-correctness findings on a correctness-quiet surface. Every survivor in every category still gets a disposition (fix, ruling, or documented decline) each round — the axis only controls the counter, not the work queue.

**6. Adversarial-parity branches converge in SUBSTANCE, not raw counts (the maintainer-approved, 2026-07-13, #831).** A branch whose correctness spec is "behavioral parity with a deleted implementation under all conceivable server/peer behaviors" faces an INEXHAUSTIBLE adversary: unprimed finders can always invent one more degenerate gateway shape, so the literal 2×0 gate may never fire even when the work is done. **How to apply:** classify each correctness finding as *mainline-real* (attested API/server behavior, or a regression in a standard flow) vs *tail* (hypothetical compat shape, narrow race with bounded cost, observability). The convergence signal is a round with ZERO mainline-real findings — raw counts mask it. Triage discipline follows: tail findings become **documented bets** (docstring + ruling) unless the fix is trivially contained, because every tolerance added for a hypothetical server is new surface the next round attacks (fix→new-edge chains were ~⅓ of rounds 6-8 on #831). Held/ruled findings never count toward the tally — a deliberate release-noted break would otherwise block convergence forever; a decisive world-fact that kills a recurring finding (e.g. "OpenAI retired these ids") belongs IN THE CODE COMMENT where unprimed finders read it, not in my triage notes. The maintainer's expectation: polish phase by ~round 6-8 even on large nuanced branches; a loop still surfacing correctness counts past that gets a severity-honest read and possibly an abort — surface the classification, don't just keep looping.

**7. Reporting/observability surface ADDED mid-review generates its own convergence tail — treat it as scope, not correctness (the maintainer, 2026-07-14, #839 → PR #844).** The core #839 fix (static `list_changed` handler awaiting inline in the SDK receive loop → self-deadlock; spawn off-loop + port the pool protocol) converged in rounds 0-3 (deadlock, per-kind debounce, gather-orphan, catalog caps, atomic removal, twins dedup). Then rounds 4-8 (correctness trend 10/5/6/6/**3/3/2/1**, never 2-clean) were ALL self-inflicted findings in an operator skip/failure REPORTING feature I introduced mid-review — a `None`/`skipped` outcome sentinel + a `last_refresh_outcome` single-source-of-truth threaded through the CLI, the node HTTP endpoint, and the admin pill. Each fix rippled to the next consumer, and round 7's fix (push-success writes the outcome) directly CAUSED round 8's regression (a single-kind push painting the whole server healthy). **Diagnosis:** a new ancillary surface touching N consumer conventions yields ~one finding per consumer per round, and fix→regress chains, independent of the original bug's quality. **How to apply:** (a) when the review tail is entirely in code the FIX added (not the bug's surface), that's a scope signal, not a correctness signal — name it to the maintainer with the trend and a recommendation rather than mechanically looping to 2-clean; (b) they steered toward one more round followed by a judgment call, then toward opening the PR after that round's polish — i.e. a single clean-up-simplify pass then SHIP, not the strict bar, because observability polish is negative-value past a point; (c) the best such fixes REMOVE surface (round 8's [0] fix reverted round 7's over-reach → net simpler); (d) resist adding the reporting feature at all unless it's load-bearing — the deadlock fix didn't need it. Corollary to lesson 6's "documented bets": bounded-cost PLAUSIBLE items (operator refresh busy-skips + arms retry; first-notification-near-boot debounce) are accepted-with-docstring, not chased.

**8. Hard round ceiling (the maintainer, 2026-07-16, compaction-visibility loop).** Standing rule, stated mid-loop while chasing 2-clean: if a change set reaches ~round 8-9 still fighting correctness findings, don't keep grinding rounds — step back. A correctness stream that deep means something structural (design, decomposition, or a surface added mid-review per lesson 7) that the fix→review loop cannot converge; the move is a severity-honest read of the trend and a re-derivation of the approach, not more loops. Complements lesson 6's "polish phase by ~round 6-8" expectation and lesson 7's scope-vs-correctness diagnosis. **Ceiling counts rounds under the FULL discipline (the maintainer, 2026-07-16 follow-up):** the ceiling exists to detect a loop that keeps manufacturing defects; rounds run BEFORE the sanity gate was in place are the manufacturing era itself, so a campaign that adopted the gate mid-flight gets its ceiling extended accordingly (compaction-visibility: sanity arrived at round 4 → step-back deferred to round 9; also justified there by a deliberate mid-loop seam replacement whose blast radius resets the discovery clock — probed at xhigh instead).

**Sanity-native campaigns: ceiling = 5, as a CHECKPOINT with teeth (the maintainer, 2026-07-16, who suggested roughly 5).** For campaigns running the sanity design pass (8c) from round 1 — the in-session pass since 2026-07-20; the retired workflow before that — a round-5 review that still contains confirmed correctness findings triggers a mandatory design re-examination — NOT an automatic abort (asymmetry: one design pass is quick; three more xhigh rounds on a sick loop are a long detour). Composition decides the outcome: (a) ANY finding traceable to FIX-ERA code → true step-back and seam re-derivation — under the full discipline manufactured findings should be near-zero, so one at round 5 is decisive (evidence the gate isn't sufficient alone: compaction-visibility round 5's sanity-vetted fixes still produced 3 of round 6's findings — compensating machinery sanity judged against the flawed design as-it-stood, plus a guard premise nobody checked against call sites); (b) all findings in ORIGINAL strata on a genuinely large branch → healthy discovery tail (lesson 4: unprimed finders probe different angles each pass; #830 round 5 found a real security bug with zero manufacture) → continue looping with 8-9 as the outer wall; (c) findings clustered in surface ADDED mid-review → lesson 7's scope signal: cut or ship-judge. The 2-clean ship gate is unchanged throughout.

**8b. Reduce repeated defects during fixes (2026-07-16).** In the compaction-visibility review, five
of the six correctness findings in round 2 came from round 1 fixes: a seam was fixed for one caller,
moved code lost a side effect, or new wrapper code omitted a cancellation window. **Why:** resolving
findings individually can recreate the same design gap elsewhere. **How to apply:** when findings
cluster around one seam, enumerate its callers, owners, exit paths, and cancellation windows before
editing. Write invariant tests from that matrix, including rows with no reported finding. When
moving code, list its side effects and verify each on the new paths. Preserve the agreed review
gate; an interrupted review supplies no clean result and must be completed or rerun.

**8c. The sanity design pass — charter KEPT, workflow ENDED (the maintainer, 2026-07-16 → retired
2026-07-20).** The maintainer's insight: the cascade is a property of the LOOP — the
pre-dynamic-workflow pipeline had a `code-review-sanity` stage that the dynamic-workflow migration
silently dropped. The maintainer's correction (after I misread its one-line listing as "validates
each fix"): sanity was the **design pass** — identifying choke points and judging whether the fixes
make sense in the design; validation-against-source was verify's job. The design-pass charter:
chokepoint locality (one edit covering the finding AND future regressions vs N scattered edits),
fragility-to-next-edit, Shared Chokepoints (one edit landing 2+ findings), completeness follow-ons,
sibling side effects, idiomatic shape — its own "why this stage exists" paragraph describes the 8b
cascade verbatim, and its first calibration example IS our bug class (per-exit-handler patches →
single state-reset chokepoint). 8b's symmetry / moved-behavior / seam-matrix questions belong in the
same pass, incl. "tests must assert the matrix, not replay findings". Requires actually WRITING the
fix plan down before editing — that artifact is half the value, and it is what the pass reads. **The
charter survives; the WORKFLOW that ran it does not.** The maintainer ended the `fix-sanity`
workflow experiment 2026-07-20, mid-#725, because it was evidently failing — apply the charter as an
in-session design pass on the written plan, and do not reinstate the workflow. **Why it failed:
verification depth is not a substitute for checking the design frame.** The workflow judged plans
against CITED SOURCE — internal consistency — and never asked the product-level question ("does this
diverge from interactive-kind semantics?", "is this larger than needed?"). On #725 it validated plan
revisions resting on two premises the maintainer had to catch themselves (the
`coordinator.mcp_enabled` flag, the DB-only console catalog) while its refinements polished the
wrong design. More agent-rounds against the source cannot detect a wrong frame; only stepping back
to the product question can — which is why the pass is a judgment call in-session, not a fan-out.
Ship gate (2-clean unprimed) unchanged. **Application:** keep the charter as topic-specific guidance
rather than a mandatory workflow in every session.

**9. Converged-tail finder-narrowing + where the round savings actually come from (the maintainer, 2026-07-22, #890/#884 pair).** Once a branch is MOSTLY converged and a particular finder has repeatedly produced zero results in consecutive rounds, that finder can be dropped from subsequent rounds — EXCEPT `bug`, which runs every round regardless (it is the axis the convergence gate is defined on, so it can never be skipped on its own track record). The maintainer explicitly generalized this beyond "security/perf": the rule is per-finder track record, not category. Evidence: #890 round 6 ran bug+quality only after security and performance had each returned five consecutive zeros; review load halved, verdict unchanged. — Same session's round-economics finding (why the pair converged in 3 and 6 rounds vs the 9-12 era): (a) the dataflow-mapper front-loads correctness for the PLANNED surface (#884: graph → design-from-graph → zero correctness findings in any round); (b) adversarially design-reviewing a step-back's PLAN before implementation prevents rounds instead of spending them (the #890 latch and transport-free-heal designs each had their killer hole caught as a sketch, not as code); (c) at-site rulings genuinely foreclose re-finds (six unprimed rounds, zero re-litigations); (d) negative-controlled behavioral detectors collapse the plausible-but-wrong finding class. CAVEAT that keeps 8b honest: surface invented MID-campaign re-enters the old regime and pays the old price — #890's r3→r5 fix-era cascade (ending in a critical) lived entirely in the heal stratum added mid-campaign; the mapper never saw it. Mid-campaign surface ⇒ either adversarially design-review it like a step-back, or expect lesson-7 economics.

**5. A fix's test must exercise the REAL collaborator, or it validates the mock, not the code.** The obo runtime OIDC-rediscovery feature was DEAD CODE — `discover_oidc` preserves the input config's `enabled` flag, so probing from the disabled boot config always returned `enabled=False` and the recovery swap was unreachable — and it shipped through 6 review rounds because its unit test **mocked `discover_oidc` to return a hand-built `enabled=True` config**, i.e. it asserted the mock's return value, never the real preserve-enabled behavior. **How to apply:** when the bug lives in a collaborator's SEMANTICS (here: what `discover_oidc` does to `enabled`), mock at the boundary BELOW it (the HTTP discovery GET) so the real collaborator runs; a test that patches the very function whose behavior you're relying on can only ever pass. Red flag: a test for "X recovers/heals/transforms via Y" that patches Y.

**10. Disposition fences: only what the tree cannot defend (the maintainer, 2026-08-10, #981 round 4).** The maintainer flagged a 17-entry do-not-re-report list as too large — the growth was me fencing every accepted nuance. The rule that fell out: the fence exists ONLY for dispositions **invisible in the tree** — filed issues (finders can't read GitHub) and conversation rulings with no code artifact. Anything carrying an in-tree pin + rationale (pinning test with docstring, code comment citing the ruling, operator doc) gets DROPPED from the fence: verifiers must rediscover-and-kill it from evidence, and if a pinned item *survives* verification despite its pin, that's a discoverability defect worth surfacing, not noise to suppress. Mechanically: each fix round should MOVE rulings into the tree (pin + rationale), shrinking the fence over rounds — #981's fence went 10 → 7 across rounds 3 → 4 while the accepted-decision count grew. Complements lesson 6's "decisive facts belong IN THE CODE COMMENT where unprimed finders read them"; same principle, list-side. Corollary: a conversation-only deferral in the fence is a smell — file the issue (per the no-deferral-comments rule) so the fence entry cites a tracked artifact.

**11. Converged-tail finder pair: REGRESSION + SIMPLIFICATION (the maintainer, 2026-09-19, #1188 branch).** Once the standard finders have mostly converged (round 6: 0 majors, findings all outside the arithmetic), the maintainer asked for two new finder types instead of a seventh identical round, prompted by their concern that their report of tokens not being counted properly in server-side tool calls had become a 21-file structural rewrite over two days and several compactions. **Regression finder:** given the ORIGINAL problem statement and the full `origin/dev..HEAD` diff, enumerate every behavior change on paths OUTSIDE the problem (plain turns, attachments, other provider lanes, task agents, forks, reopen, export, scrubs, calibration, deleted code, every changed test pin); classify each intended (cite the CHANGELOG/commit sentence) or unintended; measure numeric claims against a detached read-only worktree of dev in the scratchpad rather than argue them; include the intended changes too so the inventory is complete. **Simplification/architecture finder:** given ONLY the problem statement and the diff, list every mechanism the branch introduces with caller counts, judge needed-for-minimal-fix / residual-if-deleted / complexity-removed, quantify the untaken raw alternative, propose the minimal diff; it reads the local design note (the round-by-round rationale) only AFTER forming its own list, and then says whether each rationale justifies the mechanism or merely explains how it got there. Both write JSON to the scratchpad and hand back a short summary; both run on the frozen commit in parallel with dedupe/sanity, because a "delete that layer" verdict reshapes the pending fixes. **How to apply:** when the review tail lives in fix-era adjustment layers (lesson 7's scope signal) or the diff is many times the size of the symptom, run this pair before another fix round and bring the maintainer the keep-or-cut decision with the residuals quantified. **Outcome on #1188:** the simplification finder proposed a 3x smaller diff with sub-1% conservative residuals; the regression finder found only 3 unintended changes (1 refuted by me on measurement) and byte-identical figures on every non-server-tool path. The maintainer KEPT the branch, judging 500 new lines an acceptable size: line count and finding count decide, and a cut whose payoff is maintenance rather than correctness does not clear that bar at round 6. The transferable lesson: additive changes GATED on the new condition did not regress; the two real regressions were exactly the two UNGATED changes (a floor applied to all fixed tokens, a measure applied to every accepted turn). Gate new arithmetic on the condition that motivated it, and expect a regression finder to land on whatever is not gated. **Postscript (same evening):** after PR #1198 opened, an external probe that CHANGED CONFIGURATION after a turn was recorded (toggled reasoning replay; switched between the two Messages-API lane names) found two real defects in the adjustment layer that seven static rounds, the regression finder (fixed configurations) and the simplification finder all missed: a persisted number that bakes in a mutable operator setting, and a producer-name match standing in for a converter-level fact. The maintainer then took the cut they had declined hours earlier. Lessons: (a) a value persisted from a resolved setting is stale the moment the setting changes — persist the raw fact, apply the setting at read time, or make the charge posture-independent; (b) a predicate keyed on a provider NAME must be checked against the adapter's actual replay/convert behavior (one class can answer to two names); (c) the review instrument set needs a CONFIGURATION-CHANGE probe for any persisted derived value: record under setting X, read under setting Y, and across every lane pair that shares a converter. Add that probe to the regression finder's brief next time a branch persists a derived number. See [[feedback_nonconverging_reviews_mean_simplify]] for the deletion-first posture the second finder enforces.

**12. Rebasing a converged branch (the maintainer, 2026-09-30, #1229).** `dev` moved twice after the loop converged at the round cap, and upstream touched two of the changed files (CHANGELOG.md, pyproject.toml). After the rebase, `git range-diff` showed the patch unchanged apart from changelog context, and the maintainer skipped the extra review round the procedure called for: the reviewed code is the code that ships, and the full suite on the rebased commit is the integration check against upstream's new code. **How to apply:** after rebasing a converged branch, compare the patch with `git range-diff` and put that result, not just the list of overlapping files, in front of the maintainer. A range-diff that shows real changes to the patch needs review as before.
