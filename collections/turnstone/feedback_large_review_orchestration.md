For a **large branch-wide `/review`** (the user asked to review the whole 31-commit big-bang branch vs `origin/main` — 128 files / 22.6k diff lines), the patterns the user steered me toward / that worked:

- **Partition the diff into coherent subsystem slices and run a SET OF 4 dimension-finders (bug/security/performance/quality) PER SLICE** — the user asked for multiple sets of 4. Pointing 4 finders at the whole 22k-line diff spreads their attention thin; per-subsystem slices (each `git diff origin/main...HEAD -- <files>` written to `/tmp/rev/<slice>.diff`) give each finder a digestible, coherent scope and find real issues. Do a coverage check (every changed prod-source file assigned to exactly one slice). Write the shared branch-context brief + invariants to `/tmp/rev/context.md` once and have every finder read it (keeps prompts lean).
- **Babysit in batches** (1–2 subsystems / 4–8 finders at a time via direct `Agent` calls), reading results between batches — don't fire all 24 at once.
- **Do NOT wrap the `code-review-find-*` agents in a Workflow with a forced `schema`** — they emit findings as JSON **text**, which fights the `StructuredOutput` tool-call; all 24 failed identically ("completed without calling StructuredOutput") at **0 tokens in 30s**. Use **direct `Agent` calls** (no schema) and read the JSON from each agent's final message — that's the path that did deep work (100–200k subagent tokens each).
- **DELEGATE the back-half stages (verify → dedupe → sanity/synthesize) to agents that read/write scratch files** — the user interrupted to insist on this, so that verify and sanity run in delegated agents instead of consuming this session's context window. Compile all finder output into `/tmp/rev/findings.json` (one-time write), hand it to `code-review-verify` (writes `verdicts.json`, returns only counts), then `code-review-sanity` (reads findings+verdicts, dedupes, fix-validates, renders the markdown report). The orchestrator's context then holds only 1-line stage summaries + the final report, not 24 finders' worth of re-reading + rendering.

**Primed vs neutral contrast set (2026-06-15, attachments branch).** When the user asks for *two* finder sets — one **primed** with the design brief/invariants, one **neutral** fresh-eyes (and here also a different model: opus vs sonnet) — run both over the same slices and diff their verdicts. The neutral set caught the single most important bug (a native PDF path killed by `sanitize_messages` ordering) that the primed set scored CLEAN, and caught a real prompt-injection the primed set *asserted the opposite of*. Pattern: a brief-primed reviewer is prone to **invariant-ratification bias** — it verifies "the invariant holds" in the cited function but doesn't trace whether upstream code actually delivers it, effectively rubber-stamping the design's own claims. The no-brief set, with nothing to confirm, traces actual execution order. Primed bought depth + severity calibration but produced the only false-positives (phantom replay-fanout); neutral had zero bug-FPs. Caveat: priming and model differ together, so a single divergence is confounded — but the anchoring direction was unmistakable. **Keep a no-brief contrast set as a check on the primed reviewer.** Also: when fixes are then written, run one more finder pass **over the fix diff itself** — it caught 3 real refinements to my own fixes (an over-narrow magic-byte window, a single-chunk-read edge case).

**Two full-branch finders join every round (since #988 round 2, 2026-10-03).** Beside the slice finders, each round runs a regression finder (an inventory of every behavior change against the base, each classified intended, unintended or unclear against CHANGELOG, docs/architecture.md and the maintainer's rulings, with small probes allowed) and a simplification finder (a mechanism inventory from only the problem statement and the diff, then a minimal design and the path to it, and only then a check against the design notes and rulings). The first catches behavior drift outside the feature's own mechanism; the second turns fix-breeds-finding chains into design questions. In #988 round 3 I launched only the 16 slice finders because my written round plan listed only those, and the maintainer noticed. Build each round's launch list from what the previous round actually launched (its prompts and output files), not from a summarized plan, and reuse those prompts with only the commit, paths and rulings updated.

**Every agent prompt names the forbidden databases, finders included (2026-10-04, #988 round 6).** Verifier and regression prompts named the dev database and the smoke-test clone by address as off limits; the slice-finder prompts said only "do not run the test suite". A storage performance finder that wanted PostgreSQL query plans tried to connect to the dev database; the connection was refused and the finder stopped, so nothing was touched, but nothing in its brief kept it out. **How to apply:** every review agent's brief names the dev database and any smoke clone (by host and port) as off limits, and offers the ephemeral test database or SQL compilation instead when it needs a plan.

**A dead-code finder before the PR of a heavily refactored branch (maintainer, 2026-10-04, #988 after round 6).** Six fix rounds plus a mid-review redesign left dead code that the slice finders only noticed in passing: an unreachable fallback in `open_with_outcome`, an unreachable journal branch, a helper with no callers still documented as the resume path, and a wrapper that can never return False. On reading "real code, but nothing can reach it" in a verdict, the maintainer asked for a dedicated dead-code finder before the PR. **How to apply:** once a branch has been through several fix rounds or a redesign, run a dead-code finder on the frozen tree before the last fix batch, so its findings share that batch's gate. It covers uncalled or test-only production symbols, symbols whose last caller the diff removed, stale exports, unreachable branches, never-executed added lines (a coverage run intersected with the diff), and the same for browser JS.

**Time-box finders unless race hunting is the point (2026-10-08, #1313).** A sonnet bug finder
briefed to probe claims on the real code path, with no limit, ran 2.5 hours and about 700k
tokens of random-operation fuzzing, finding races at 1-2 per 2500 runs, while the other four
finders took 15-90 minutes; the maintainer pointed out its runtime and token count. A
SendMessage asking it to wrap up returned its findings within minutes. In the next round,
briefs that said "time-boxed: targeted probes only, no stress loops, no fuzzing, no broad test
runs" kept both finders under an hour without losing what mattered. **How to apply:** put that
line in every finder, verifier and sanity brief by default; drop it only when stress-testing for
races is the explicit goal, and then name a run budget.

**Why:** a full-branch review is genuinely worth it even when each commit was reviewed in its own session — it caught integration-seam regressions the per-commit reviews missed (a removed orphan-repair net that 400s on legacy Anthropic resume; a retry-walk that didn't learn the new card classes). But naively it floods the main context. **How to apply:** slices × sets-of-4 via direct Agent calls in batches → findings.json → delegated verify + sanity.
