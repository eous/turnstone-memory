One theme: get SDK/library/wire **boundaries** right — spike first, verify assumptions, test THROUGH the real boundary, write faithful stubs/mocks/asserts, prove parity by output, and root-cause boundary failures instead of working around them. See also [[feedback_pre_commit_gates]].

**Spike before planning** (boundary_spike_before_planning). For any phase touching an external SDK/library/platform boundary (httpx, anyio, MCP SDK, asyncio internals, fsspec, OS APIs), run a short timeboxed (~30 min) empirical spike BEFORE writing the plan. List the boundaries the phase crosses; for each write 1-3 questions whose answers determine the design ("does this hook fire before `raise_for_status`?", "does this method accept a sync callable?", "what does `headers.get('foo')` return when upstream sent two?"); answer them in a REPL/one-shot script; cite the answer (SDK file:line or script output) in the plan. Cite VERIFIED facts, not guesses. Skip when the boundary is well-understood from prior work. *Why:* two OAuth-MCP incidents shipped from plan-level assumptions — (1) the MCP SDK swallowed `httpx.HTTPStatusError` in its post-writer, making a classifier's auth branch structurally unreachable; (2) `httpx.Headers.get("www-authenticate")` joins repeated headers with `, `, so a parser tested on single strings took attacker-injected payload. A spike would have caught both pre-code.

**Tag plan decisions VERIFIED or ASSUMED** (verified_vs_assumed_in_plans). Every plan decision that depends on external behaviour gets **[VERIFIED: \<sdk_file\>:\<line\> ...]** (citation: file:line / script output / empirical test) or **[ASSUMED]** with a risk-register entry and a one-line verification recipe the implementer runs (`python -c "..."`) — then upgrades to VERIFIED or pivots. Reviewers grep `ASSUMED` for unresolved load-bearing guesses. Don't tag well-internalized facts (ruff is the linter, mypy is strict). *Why:* a plan said "use the response-hook factory with a sync hook — valid per the docs"; the library `await`ed hooks so the sync callable raised `TypeError`. The guess looked like a fact because it sat in the same prose voice as genuinely VERIFIED neighbours.

**A review-agent claim about external-API behaviour is ASSUMED, never VERIFIED — and must not be laundered into a shipped artifact** (review_claims_are_hypotheses). A code-review finding that asserts how a provider/SDK/wire behaves ("Anthropic rejects tool ids outside `^[a-zA-Z0-9_-]+$`", "api.openai.com caps `tool_call_id` at 40 chars") is the agent REASONING about an API, not evidence — treat it exactly like an [ASSUMED] plan claim: verify against real behaviour or in-tree evidence before acting, and NEVER copy it into a CHANGELOG / commit / PR body as a stated fact. Before believing a "provider X rejects Y" claim, check the cheapest disconfirmer first: does the code already DO Y and work? *Why* / case (PR #820, 2026-07-10): round-1 review "confirmed" (verifier-agent confirmed, i.e. a second agent agreed) that strict providers 400 on `::`-containing tool ids; I added a wire-legalization pass AND wrote "previously 400-failed a task agent at first tool-turn replay" into the CHANGELOG. The OLD id format was ALSO `{parent}::{id}` (contains `::`) and Anthropic agents ran reliably — the disconfirming evidence was in the diff. Nothing in-tree asserted the constraint; the deployment is lenient anthropic-COMPATIBLE vLLM. The maintainer caught the shipped false claim, pointing out that anthropic agents had been working reliably. Two agents agreeing is not verification; a passing production path that violates the claimed constraint IS disconfirmation. **Extension (2026-07-24, Opus 5 review): the rule covers CHEAP claims too, not just external APIs.** A /review verify stage rated a judge finding a *nit* on the premise "`Path("")` resolves to `.` so both tools return an error string" — half wrong: `Path("")` IS `PosixPath('.')`, `.is_dir()` is True, so `list_directory` with `{}` args executed and returned real output. The wrong premise propagated verify -> dedupe -> final severity. A one-line `python3 -c` would have settled it. Rule: if a claim is executable in under a minute, EXECUTE it — stdlib/pathlib/regex behaviour included; reasoning about it is the same failure class as reasoning about a provider API.

**Tests must drive through real boundary objects** (tests_through_boundaries). Any path crossing an SDK boundary needs ≥1 test driving the pre-boundary signal through the REAL boundary using real objects. Direct synthesis of the post-boundary signal is fine for isolated unit tests of post-boundary logic, but cannot be the sole gate — it passes against structurally broken wiring. Ask: "is the test creating the post-boundary signal directly, or driving the pre-boundary signal through the real boundary?" Treat boundary-bypass-only coverage as a structural gap; require an integration test before merge. *Why:* same two OAuth-MCP bugs — unit tests injected `httpx.HTTPStatusError` directly (bypassing the SDK swallow point) and called the parser with single strings (bypassing httpx's multi-header join). Canonical pattern: `tests/test_mcp_pool_auth_integration.py` (FastMCP subprocess + real `streamablehttp_client`); spike template `tests/spike_sdk_concurrency.py`.

**Mock-transport tests must inspect the request BODY, not just the path** (mock_transport_body_inspection). When the SDK POSTs/DELETEs to a server endpoint that reads JSON via `read_json_or_400` (which calls `request.json()` → `ValueError` → `400 Invalid JSON body` on empty/malformed bodies), the regression test must capture and assert `request.content`, not rely on a path-keyed mock that answers regardless of body. Path-keyed `_mock_transport` is fine for pure routing (right URL + method) but inadequate for body-shape contracts. Pattern: `captured["body"] = json.loads(request.content) if request.content else None` then `assert captured["body"] == expected_body`. *Why* / case (PR #422): a `close_workstream` refactor sent `json_body=None`; the path-keyed mock answered "ok", but the real interactive handler (`supports_close_reason=True`) reads JSON and would 400 on every call. Template: `tests/test_sdk_server.py::test_close_workstream_sends_valid_json_body`.

**Test stubs must mirror the production loader exactly** (stub_shape_must_mirror_loader). When stubbing a dataclass-shaped value (e.g. `ModelConfig`) via `SimpleNamespace`, populate ONLY the fields the production loader sets — never multiple possible field locations "to be safe". When the loader pops a key out of a nested dict into a top-level field, the stub mirrors THAT shape (empty nested dict + populated top-level). Shared stub helpers match production exactly; per-test variants narrow, never expand. Detection heuristic: two stub fields holding the same data ⇒ one is wrong (pick the loader's) and the stub is masking a field-location bug. *Why* / case (Phase 5, 2026-05-20): `_resolve_server_type` (`session.py:1170`) read `cfg.capabilities.get("server_compat")` but the loader (`model_registry.py:401,485`) pops it to top-level `cfg.server_compat`. Stubs populating BOTH locations let the bug pass 17 integration + 10 audit-log tests + a 6286-test run; only /review caught it.

**No computation in test assertions** (no_computation_in_asserts). Asserts are plain equality checks against pre-computed values — no loops, comprehensions, `all(...)`, `set(...)`/`list(...)` aggregators inside the `assert`. *Why:* visible computation forces reviewers to mentally execute the expression to find the property under test. Instead of `assert all(f(x) == y for x in xs)`, compute `seen = {f(x) for x in xs}` then `assert seen == {y}` (or write N explicit asserts). One element inline is fine; inside an aggregator it's smelly.

**Prove wire-shape parity by diffing serialized OUTPUT** (parity_needs_output_diff). Never infer that two surfaces emit the same shape from the fact that they share decoration/helper functions (that proves only the shared PART matches). Construct a representative payload and diff the two actual serialized outputs field-by-field (throwaway script or committed test), or route both through ONE projection function; tag VERIFIED only after the diff. Pure transforms (a normalizer/serializer, a DOM-free JS function under `node`) are unit-testable even when the full app isn't — test the pure part, don't lean only on end-to-end smoke. *Why* / case (#549 PR A): a spike claimed enriched-history parity between `server.py::_build_history` (SSE) and `make_history_handler` (REST `/history`) because both call `decorate_history_messages`/`extract_reasoning_for_history`. False — `_build_history` did extra projection (flatten `tool_calls[].function`, rename side-channels, collapse multipart, derive `denied`/`is_error`/`pending`); the renderer crashed on the raw REST shape (`JSON.parse(undefined)`). Shipped because unverifiable in-sandbox; user caught it in a browser smoke.

**Test frontend JS against a running server before pushing** (test_frontend_locally). Verify against a live server, not just a syntax check. Standard admin-panel pattern (compare against working tabs — Roles, Policies, Skills in governance.js): use `authFetch()` not raw `fetch()` with `_adminToken` (undefined in the console); URLs use the `/v1/api/admin/...` prefix; add `if (!r.ok) throw new Error("Failed");` before `r.json()` on GETs; watch the browser console for `ReferenceError`/`undefined`. *Why:* the Judge tab shipped with `_adminToken` undefined + wrong URLs, rendering but stuck on "Loading settings..." with a silent `ReferenceError`, because the JS was only syntax-checked.

**Run pytest via the project venv** (pytest_env_parity). Invoke `.venv/bin/python -m pytest`, never `uv run pytest` or bare `pytest` — the system pytest's shebang may run a system Python that imports system-installed library versions instead of the lockfile-pinned venv versions CI uses. *Why:* `uv run pytest` resolved to `~/.local/bin/pytest` running `/usr/bin/python3`, loading system mcp 1.26 instead of venv mcp 1.27; counts differed (5557 vs 5427) and a system-only `pytest-asyncio` made `@pytest.mark.asyncio` tests pass locally but fail on CI. When "passes locally, fails on CI", FIRST check `which pytest` and the failing process's `sys.executable`. The venv interpreter is the canonical CI-parity entry point. **Re-checked 2026-07-24: the hazard no longer reproduces on this box** — `uv run pytest` and `.venv/bin/python -m pytest` both collect 9763/9773 and both resolve to `<turnstone checkout>/.venv/bin/python*`. Keep the rule (a reappearing system pytest would resurrect it), but the load-bearing part is the CHECK, not the incantation: when counts look off, compare the two invocations' collected totals and `sys.executable` before assuming drift.

**Investigate SDK-boundary hangs to ROOT CAUSE** (root_cause_sdk_hangs). When a boundary-crossing test hangs/deadlocks/won't-propagate, the default is to instrument the boundary and bisect through layers (our code → SDK transport → SDK session → anyio/asyncio primitives) to the actual bug — NOT to restructure the test around the failing case or ship the headline test `xfail`. Steps: (1) back up SDK source to `/tmp` to revert cleanly; (2) add `print(..., flush=True)` at suspect layers, ours AND the SDK's, with prefixes (`DBG`/`SDK`); (3) run `.venv/bin/python -m pytest -v -s --capture=no` (see pytest_env_parity); (4) bisect — the hang lives at the last layer that prints, the bug is what it does next; (5) read the library source, not the docs; (6) restore the SDK and confirm the test still hangs the same way; (7) make the fix small/targeted (a race, cancellation, explicit teardown) informed by the mechanism, documented in the commit message and as a hard invariant if it must not regress. *Why:* a reused-session 401 path hung at 45s; the instinct was to restructure the test, but the user asked to fix the reconnect path. Instrumentation exposed anyio's `MemoryObjectSendStream.send_nowait` skipping receivers with `pending_cancellation` under the SDK's TaskGroup cancellation cascade. The blind "fix" (per-call `asyncio.wait_for` with an arbitrary timeout) would have shipped a degraded UX with nobody knowing why the SDK hung.

**Before sending a new field across a seam, trace every reader of it on the far side** (trace_far_side_readers). A fix that adds or changes something a request body, a shared storage row, or a lock carries across a process boundary is a seam change however small the diff. Before writing it: search the far side for every reader of that field and read each one, not only the one the design needs. Ask what each reader does differently when the field is present. This is the fix-sized substitute for the dataflow-mapper agent, which is right for feature work and invasive refactors but too heavy for a fix (the maintainer, 2026-09-05); a fix that stays inside one process needs neither. *Why* / case (#1099, 2026-09-05): to make scheduler retries idempotent I sent a caller-chosen `ws_id` on the create request. I checked that the SDK accepted it and that the node's duplicate path answered 409, and stopped. The node's create path ALSO gates its routing pin on `if not requested_ws_id` (`turnstone/server.py` ~2956), so every scheduled workstream went unpinned and console-routed calls landed on the wrong node in a multi-node cluster. One search for readers of the requested id on the node would have shown it in a minute; instead a full review round found it, after the design was built and tested. The mechanism came from a round-one review finding's "Fix:" line, which is the review_claims_are_hypotheses rule above in a new coat: a reviewer's proposed mechanism is a pointer to the seam, not a design, and gets the same reader trace before it is adopted.


**Internal seams count too** (2026-09-06, #1108 attempt 1). `model_turn` materializes attachments BEFORE it calls `prepare_wire`; a lowering pass written against the by-reference placeholder shape was inert on the live path and its tests passed because they drove `dicts_from_turns(self.messages)`. Rule: for any change at a shared internal seam (`model_turn`, the attachment resolver, the wire cache), trace the call order first (the `dataflow-mapper` agent or a 10-minute read), then write the first test against the *materialized* wire — `materialize_attachments(...)` output fed to `_prepare_lowered_wire_messages` — not against the trajectory. Two review rounds (19 then 13 clusters) were spent on consequences of skipping this; see docs/design/1108-video-attempt-1-lessons.md (LOCAL).
