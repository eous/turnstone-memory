**Shipped in #760 (2026-07-03)** (branch `fix/judge-full-arguments`) — 4 commits: (1) "give the intent judge the full tool arguments"; (2) "source the output-guard judge's real window + oversize backstop"; (3) "coerce non-positive judge windows + real output-guard fallback" (Copilot PR-review fixes); (4) "normalize config.toml context_window=0 to auto-detect" (root-cause registry fix). Hardened pre-merge via /code-review max (sonnet 5) + Copilot bot review. Durable gotcha: `context_window=0` is the AUTO-DETECT sentinel (inherit CLI-detected window). DB loader normalizes it (`model_registry.py:400` `... or context_window`); config.toml path did NOT (`:489`, now fixed to match) — an explicit `0` used to leak downstream and zero every budget. `judge._positive_window` stays as defense-in-depth for residual un-normalized paths (CLI shim `:507`, direct ModelConfig).

`_evaluate_intent` (session.py, ~6925) builds `it["func_args"]` per-tool. This dict is read by BOTH tiers with opposite needs: the heuristic engine regex-matches a narrow field (`_get_arg_text` reads only `command` for bash, `path` for write/edit_file), while the LLM judge serialises the WHOLE dict into its prompt (`judge._prepare_context`, ~1408) as its entire view of the call's arguments.

**Failure mode (real incident):** a path-only `edit_file` projection (`{path}`, no `edits`) made a qwen3.5-9b judge rule a legitimate multi-edit call "malformed — missing old_string/new_string" and DENY at 95%. Amputated args → confident false-deny, worst on small-window local judges. skills was worse: `fa` was built and never assigned → judge saw `{}`.

**Fix shipped** (branch off `df573b73`, main only, no 1.6 backport): full per-tool projections incl. edit_file `edits`, write_file `content`, skills `allowed_tools`/`auto_approve` risk signal; a parametrized guard test asserts every `needs_approval=True` tool projects non-empty func_args (silent gap → CI failure).

**Truncation = BACKSTOP, never default (user principle, HYPOTHESIS.md-framed).** The projection is the model-visible LOWERING (π) into the judge's context; the FULL args always stay in the trajectory (S) — truncation only bounds the view, never destroys data. So: (1) judge prompt lowers args WHOLE up to the judge's REAL window — `arg_budget_chars()` = `window*0.25*3.5`, NO sub-window ceiling; honest `…[N of M omitted]` only on genuine overflow. (2) Window is `ModelConfig.context_window` from the registry (default 32768), NOT `provider.get_capabilities().context_window` — the static caps table returns 200000 for EVERY local model (`_openai_common.py OPENAI_DEFAULT`, `_anthropic.py _ANTHROPIC_COMPAT_DEFAULT`), which silently over-budgets a small local judge into overflow. Both judges resolve via `model_registry.resolve()` ModelConfig (getattr-guarded). (3) The verdict's record copy (persisted to `intent_verdicts.func_args` + streamed via `on_intent_verdict` `**verdict`) is capped separately at `_VERDICT_ARG_CAP=16384` — the frontend NEVER reads it (grep func_args in webui JS = empty), so it's frontend-unread audit weight. NO default small caps (removed 512/500). [[feedback_dont_trim_for_small_models]]

**Recurred 2026-07-10 (#817 branch):** adding `run_in_background` to bash — the NEW ARG wasn't added to the bash projection, so the judge would have approved detached execution without knowing the process outlives the call. The maintainer caught it mid-session, noting that adding new tool arg fields had caused this before. The #760 guard test (non-empty func_args) can't catch a MISSING FIELD on a tool whose projection is already non-empty. **Rule: any new arg on a `needs_approval` tool must be added to its `_evaluate_intent` projection in the same change, with a projection regression test built via the real `_prepare_*` (so the prepared item can't drop the field either).**

**Output-guard judge (output_guard_judge.py):** judged output passed WHOLE (fence.wrap) — never truncate content under review (a head/tail cut could hide an injection payload). tool_args also whole. Oversize backstop: `evaluate()` skips the LLM + labels an `llm_error` ("output_too_large_for_judge_window") when the prompt exceeds the registry window — honest, non-destructive (heuristic always ran first, so no coverage hole, just the opted-in LLM tier skipped visibly).
