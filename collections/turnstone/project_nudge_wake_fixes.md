Three nudge-subsystem fixes + five rounds of review hardening, shipped as **PR #799** (branch `fix/nudge-wake-watch-hardening`, single commit 008dbbae). Round 5 was a single-agent e2e adversarial review that found 2 majors in PRE-EXISTING load paths (detail-GET lazy-rehydrate never ran open_post_load → unregistered live session → duplicate restore shells; restore shell blindly clobbered a pane registration landing mid-restore → now yields to it) + 2 hardened residuals (fresh-fire unrestorable path stashes before its deactivation write; deliver_wake_nudge_from_queue contains GenerationCancelled). Pre-PR conventions: openapi-server/console.json are CHECKED-IN GENERATED artifacts (regenerate via sdk/typescript/scripts/generate-types.py whenever server_schemas.py changes); types.ts is hand-maintained; CHANGELOG entries land at release cuts, not per PR; docs/api-reference.md documents create-response fields.

1. **Denial nudge → tool channel** (`session.py` `_execute_tools` deny branch): was `_queue_user_advisory` (deferred to next user-message seam, arriving after the model already reacted to the denial); now `_queue_tool_advisory` so it drains through `_collect_advisories` alongside the denied tool results, same seam as `tool_error`/`repeat`. Docstring taxonomy updated: user channel = responds to the user's *message*; tool channel = responds to a *tool batch* (incl. denial, which is user behaviour but batch-scoped).

2. **Watch-fire wake on already-idle sessions**: `IdleNudgeWatcher` only fires on IDLE *transitions*; a watch firing on an already-idle ws enqueued but nothing woke it (sat until next user message). Fix: extracted shared gate `wake_workstream_if_pending(ws)` in `core/idle_nudge_watcher.py` (gates: session None / `ws._closed` / state≠IDLE / no USER_DRAIN-pending → else `session_worker.send` wake); `ChatSession.set_watch_runner(runner, wake_fn=...)` calls it after each enqueue (exception-swallowed — a raise would abort `_poll_watch` before the row write and re-fire the reminder every tick).

**Key design decision**: the server's three wiring sites pass `wake_fn=lambda: wake_workstream_if_pending(ws)` closing over the **Workstream object, not its id** — after eviction+restore, `manager.create` mints a fresh manager-tracked id while `session.resume(ws_id)` adopts the watch rows' original id, so `manager.get(watch_ws_id)` would miss. Also makes the unattended watch-restore path coherent: `auto_approve=True` there exists precisely so the wake turn can run tools with no user attached.

3. **session_worker exit-time wake backstop** (fixes coord `idle_children` strand — model forgets `wait_for_workstreams`, coord idles, never revives until next user msg): `set_state` subscribers fire on the CALLING thread, and IDLE is emitted from INSIDE the worker's `run()` at end-of-send — so `IdleNudgeWatcher`'s transition-time wake ALWAYS hit `session_worker.send`'s reuse path (worker still owns `_worker_running`) and no-op'd; with IDLE at end-of-send there is no later seam. The pre-existing coord integration test passed only because it called `set_state(IDLE)` from the test thread (no worker) — production shape was untested. Fix: `session_worker._runner`'s finally, after clearing the flag (owner only), calls `_retry_pending_wake(ws)` → defensive peek (`getattr(session, "_nudge_queue", None)` — watch-style stub sessions bail) → `wake_workstream_if_pending`. Convergence owned by producer gates: observer cooldown + `_last_assistant_used_wait` skip + hard cap 3 (never resets on wake-driven IDLE exits), and the wake's drain empties the queue so the wake worker's own exit retry no-ops. This also CLOSED the previously-accepted residual (wake_fn racing a worker mid-exit). Test gotcha pinned in both test files: `send` assigns `ws.worker_thread` under lock BEFORE `t.start()` — joining `ws.worker_thread` after a fast worker races "cannot join thread before it is started"; poll outcomes instead.

**Hardening round (2026-07-07, same working tree)** — four follow-ups, then an `xhigh` workflow code-review (`/code-review xhigh`, ~1.1M tok, 17 agents) that found 8 verified REGRESSIONS in the hardening itself (mostly my `watch.py` concurrency + delivery-retry). All 8 fixed same session. The four follow-ups AS SHIPPED (post-fix):

1. **Watch delivery-retry — HOLD-REMINDER + BOUNDED** (`watch.py`; original "commit-only-next_poll + re-run command" design was WRONG — review findings 2+3): on delivery failure `_poll_watch` HOLDS the built reminder + intended row-update in `_pending_delivery[watch_id]` and commits only `next_poll`; a later tick RE-DELIVERS the held reminder via `_redeliver_pending` **without re-running the command** (so a transient `stop_on` match isn't lost — the original re-run design silently swallowed it), bounded by `MAX_DELIVERY_ATTEMPTS=5`, after which it commits the held update (deactivates the terminal watch) + `delivery_abandoned` error log so a permanently-unrestorable ws (corrupt persona stamp) can't re-run a mutating command forever. `forget_terminal_dispatched` (user-cancel) also clears the hold. Note: here `fired ⟹ is_final` (every watch fire is terminal/one-shot), which is why hold+deactivate is clean.
2. **Restore serialization** (`watch.py` `_dispatch_result`, review finding 1 = the CRITICAL one — data corruption): concurrency made restore re-entrant — two watches on ONE evicted ws (distinct watch_ids, so `_in_flight` didn't dedup) both saw `_dispatch_fns[ws_id]` None and both ran `_watch_restore_fn` → **two live auto-approved sessions racing writes into one conversation history**. Fix: `_restore_lock` held ACROSS the whole restore (rare+slow, so serial is fine) with a re-check of `_dispatch_fns` after acquiring → at-most-once restore per ws AND caps concurrent restores at 1 (also fixes finding 5, DB-pool starvation). Also: a registered fn that RAISES now returns False (holds) instead of falling through to restore — falling through would also duplicate the session.
3. **Bounded concurrent polls** (`watch.py`): tick thread only enumerates; polls on daemon threads gated by `BoundedSemaphore(max_concurrent_polls=4)` + per-watch_id `_in_flight` dedup. Saturation leaves rows due (next tick). Spawn failure now LOGS + `continue`s (finding 6 — the original `raise` aborted the whole tick's remaining watches). `stop()` drain deadline uses `tool_timeout+5` not `check_interval+5` (finding 7 — a poll's command can outrun the tick cadence) and only warns when leftover>0 (finding 8 — false `count=0` abandonment log).
4. **Init-message worker via `session_worker.send`** (`server.py` create tail): inherits the exit wake backstop. Enqueue branch (reachable only via caller-supplied ws_id raced by concurrent /send) now PRESERVES the message via `session.queue_message` when there are no attachments (finding 4 — was a silent drop), logs otherwise (attachments can't ride the interjection seam).
5. **Wake observability**: `wake_workstream_if_pending(ws, *, trigger=...)` — logs `nudge_wake.dispatched` / `nudge_wake.deferred_worker_busy`. Triggers: "idle-transition"/"worker-exit"/"watch-fire". Logs only.

**Round 2 review** (`/code-review high` pre-push, ~0.78M tok, 16 agents) found 6 MORE distinct defects — round-1 fixes were correct-but-incomplete + 2 new edge cases. ALL fixed:
- **Restore lock too coarse** (round-1's `_restore_lock`-across-restore starved the poll pool — a poll thread held its `BoundedSemaphore` slot while blocked on the global lock). Replaced with admission control: `_restoring: set[str]` (per-ws_id dedup) + `MAX_CONCURRENT_RESTORES=2` cap, lock held ONLY for the fast admit check, restore runs OUTSIDE the lock, over-cap/same-ws polls DEFER (hold + re-deliver next tick) instead of blocking. Consequence: concurrent same-ws now = one delivers, one defers (was: both deliver via shared lock).
- **Bounded giveup deactivated the watch on TRANSIENT causes** (slots saturated under load → watch silently turned off after ~5 ticks). Now split: transient exhaustion drops the held reminder but LEAVES THE WATCH ACTIVE (next_poll advance, re-fires); only a PERMANENT `WatchWorkstreamUnrestorable` (new exception, raised by `_watch_restore_fn` on corrupt persona stamp; RuntimeError/slots-busy still returns None=transient) deactivates immediately.
- **_pending_delivery leak** when update_watch raises AFTER successful re-delivery (id stuck in _terminal_dispatched + _pending_delivery, row deactivates via already_dispatched branch which didn't clear pending). Fixed: already_dispatched branch clears pending; _redeliver clears the hold BEFORE the commit.
- **Init message text dropped** on the attachment+worker-reuse race — now queues the text always (attachments logged as dropped, message preserved).
- **Dup dispatch block** → extracted `_try_dispatch_fn` (returns True/False/None).
- Defended (not changed): a live registered fn that RAISES returns False (holds) rather than falling through to restore — restoring would spawn a duplicate session (the round-1 crit). The finding-2 fix means this now self-heals (transient, keeps watch active) instead of dropping.

**Round 3 review** (`/code-review high`, ~1.09M tok, 22 agents) found 6 MORE confirmed correctness bugs — round-2's fixes again correct-but-incomplete. ALL fixed:
- **Transient exhaustion re-ran the command FOREVER** (round-2's "leave watch active" discarded the stashed update_fields, so poll_count never advanced and max_polls could never trip). Now exhaustion charges ONE poll to the watch's own `max_polls` budget (commits `poll_count` + full-interval `next_poll`, baseline deliberately uncommitted so a delta `stop_on` re-detects); with the budget spent it commits the held update (deactivates, `reason="poll_budget_exhausted"`). Bounded by the user's own budget.
- **Blanket `except ValueError` in `_watch_restore_fn`** covered create+resume+set_watch_runner → any post-create ValueError permanently deactivated the watch AND leaked the just-created ws (max_active slot). Now: ONLY the persona-stamp pre-read maps ValueError→`WatchWorkstreamUnrestorable` (nothing created yet); post-create failures close the shell (`manager.close`) + return None (transient, bounded by the poll budget).
- **Full dispatch under `_restore_lock`** (the admission re-check called `_try_dispatch_fn` → runs the closure → `ws._lock`/thread spawn under the node-wide lock → poll-pool pinning). Now the re-check is a PRESENCE check (`get_dispatch_fn`); race-won delivery runs outside the lock (None→False=defer). Lock order `_restore_lock→_dispatch_lock`, no reverse nesting.
- **Attachments destroyed on the raced create path**: the pre-drain ran before `session_worker.send`, so the enqueue branch had already destroyed the staged copies. KEY INSIGHT: the pane rehydrate can't start until the create response returns, so draining AFTER send (branch-aware via `nonlocal init_enqueued` — `enqueue()` runs synchronously inside `send`) is equally race-free. Enqueue path now leaves attachments STAGED (composer chips persist, next send delivers); spawn path drains post-send pre-response.
- **stop() drain blocked the event loop up to ~125 s** (`tool_timeout+5` synchronous in async lifespan; systemd 90 s SIGKILL would skip state-writer drain + node dereg). Now `min(tool_timeout, STOP_DRAIN_CAP_SECS=30)+5` AND `await asyncio.to_thread(watch_runner.stop)`.
- **Held-reminder redelivery deferred by FULL interval_secs** (daily watch → 24 h alert delay on a seconds-long transient). Now `min(interval_secs, DELIVERY_RETRY_CAP_SECS=60)` — redelivery is cheap in-memory dispatch; the full interval is reserved for the exhaustion re-fire (a fresh command cycle).
- Cleanups: delivery-outcome state machine deduped into `_abandon_delivery`/`_hold_delivery`/`_commit_terminal_update` (replaces `_defer_row`); dead `is_final` generality dropped from the stash machinery (held deliveries are ALWAYS terminal: `fired ⟹ is_final`, guard simplified to `if is_final:`); `_iso_in()` helper; `wait_until` moved to `tests/_helpers.py` (both worker/wake test files import it).
- New tests: budget-spent-deactivates, capped-cadence, race-won-admission-delivers-outside-lock (monkeypatched `_try_dispatch_fn` forces the between-fastpath-and-lock window; probe asserts `_restore_lock` acquirable during dispatch), create-raced-by-live-worker-keeps-attachments-staged (monkeypatched `session_worker.send` forces enqueue branch).

**Round 4 — final pre-push `/code-review max`** (~1.72M tok, 30 agents; 2 verifiers + synthesize died at 27/30 — salvaged from the run journal: 22 verified kept + 2 refuted + 2 unverified sweep candidates hand-verified, synthesized manually). 24 confirmed findings → 8 distinct issues, ALL fixed same session, then a 3-agent adversarial pass on the fix diff found 3+3+2 MORE (fixed):
- **Registry follows identity** (worst family, PRE-EXISTING but weaponized by the wake work): dispatch registry keyed on `_ws_id` AT REGISTRATION; identity rebinds at `resume()` AND `/new` (grep `self._ws_id = ` — constructor + those two). Five sites: restore-fn ignored `resume()==False` (delivered into blank fresh-id session, deactivated watch as "delivered", leaked one orphan auto-approved ws per fire); CLI `--resume` registered before resume (every fire → shadow session on the operator's live conversation); reopen path never re-registered after `close()` removed the fn; in-session `/resume` rebinds in place; `/new` ditto (new watches created post-/new never reach the session; old-ws fires land in the wrong conversation). Fix: `_follow_watch_registration(old_ws_id)` helper called from non-fork `resume()` AND `/new` (new key live BEFORE old key removed — no empty-registry window; refuses to STEAL a registration another live session holds) using stored `_watch_wake_fn`; restore-fn treats resume-False as permanent ONLY after a RAISING storage probe confirms no rows (memory.load_message_turns swallows errors into [] — a blip must not kill the watch); CLI registers after resume; `_interactive_open_post_load` wires the runner; shared `_watch_fire_wake_fn(ws)` helper (object-not-id comment lives once).
- **Registry ownership** (adversary round): multiple live sessions can transiently serve one ws_id (restore shell vs reopened pane; `/resume` of an id open in another pane) — blind `remove_dispatch_fn` from one teardown unregistered the OTHER (its next fire → duplicate session). Now `remove_dispatch_fn(ws_id, owner=fn)` removes only the caller's own closure (`_watch_dispatch_fn` stored on session); resume-tail refuses to STEAL a live registration (warning, original owner keeps fires).
- **Cancel vs poll-pool races** (new-in-diff): held/redeliver paths re-check `is_watch_active` before stashing/dispatching (storage-error biases toward delivery); cancel paths write the row BEFORE `forget_terminal_dispatched` (ordering contract in its docstring); HTTP `cancel_watch` endpoint now calls forget at all (was leaking holds unconditionally); `_sweep_cancelled_holds` each tick bounds the residual stash-after-clear interleaving to one check_interval. `list_due_watches` filters `active==1` so late `next_poll` writes can't resurrect cancelled rows.
- **Hold durability**: `_hold_delivery` commits the `poll_count` charge durably (restart mid-hold re-runs bounded by max_polls, +≤1 regeneration run per restart at the cap — deliberate: regenerates the lost final reminder). Baseline still uncommitted (delta re-detect).
- **Write-then-clear** (adversary): `_abandon_delivery` + exhaustion branch commit the row BEFORE clearing the hold — under reads-OK/writes-fail storage (disk-full sqlite) clear-first re-ran the command every attempt-budget cycle forever; now the write retries via redeliver with the hold intact. (Delivered-branch keeps clear-first: `_terminal_dispatched` covers its write retry.)
- **Restore-stall handling = DETECTION ONLY** (two design iterations, both mine, both killed): v1 evicted stale admissions (adversary: each eviction readmits capacity that wedges ANOTHER pool thread — slot never released — converting the capped 2-slot end-state into total poll-pool collapse); v2 debt-bounded the eviction (safe but ~60 lines of subtle machinery whose benefit exists only in a timeout-less >10min-wedge-then-recover world). Final: `_restoring` = dict of monotonic admission stamps, entries >`RESTORE_STALL_ALERT_SECS=600` log.error at every refused admission, NEVER evicted; recovery = restart. Constant comment prices why reclaiming would be strictly worse.
- **`_closed` at the teardown choke point** (adversary HIGH): only close/close_idle ever set `ws._closed`, and only AFTER teardown — eviction and delete() never did, so the object-reference wake paths (wake_fn, exit backstop) could spawn full auto-approved turns on evicted/deleted workstreams. Now `cleanup_session_ui` (funnel for close/close_idle/evict/delete/discard) sets `_closed=True` under `ws._lock` FIRST; `session_worker.send` re-checks under the same lock (authoritative guard; the gate's lockless read is fast-path only). /send surfaces closed-refusal as the resolution 404, not `queue_full`.
- **`_enqueue_init` honesty**: no blanket except — queue.Full reaches send's backpressure branch; create response carries `initial_message_status: "queue_full"|"refused_closed"` (factory passthrough; schema + TS types updated; FE doesn't read it yet), attachments-drain gated on `init_ok`.
- Refuted/kept: live-fn-raise no-restore (4th consecutive refutation), `_iso_in` inline (now-capture consistency), stash-first in `_hold_delivery` (survives storage blips).

Kills the class for all current/future Mock-session fixtures.
